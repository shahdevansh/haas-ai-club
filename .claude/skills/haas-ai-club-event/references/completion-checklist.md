# Completion, delivery, and resume checklist

Track the event through this checklist. It doubles as the resume state if a
run is interrupted: check each item against the live system before re-doing
it - never create a duplicate because you lost track.

## Setup

- [ ] Intake complete (blocking answered, optional defaults stated, research confirmed)
- [ ] Plan presented and explicitly approved
- [ ] EMS request submitted - request ID recorded privately; confirmation email received; room name now publishable
- [ ] CampusGroups draft created; public RSVP URL obtained and verified resolving to this event
- [ ] Poster options rendered from the verified link's QR; organizer picked one; final attached to the event
- [ ] RSVP published (poster attached, room shown only as confirmed)
- [ ] Marketing message drafted; organizer approved the exact words; sent/posted by the agreed sender
- [ ] Website updated (right section, right order, deduped speaker card); deployed; verified live on desktop and mobile
- [ ] Optional email blast: drafted, exact words and recipient list approved, poster attached, sent
- [ ] Food ordered only after explicit spend approval; itemized receipt captured

## Day-of and after

- [ ] Room/access confirmed on the day; online link works (if applicable)
- [ ] Actual turnout recorded (private)
- [ ] Website: regular event moved Upcoming -> Past (workshops/hackathons and treks stay in their own sections); speaker cards moved only if no future appearance remains
- [ ] Reimbursement filed (CalLink purchase request, itemized receipt, actual turnout); tracked through Financial Agent advancement to payout
- [ ] Organizer told what is done, what is pending, and any IDs/links they need

## Privacy of receipts

Request IDs, reservation numbers, admin/edit links, receipt images, and
payout details stay between the agent and the organizer. Public surfaces get
only the public RSVP URL and confirmed facts.

## Partial failure

If any single workstream fails (login blocked, EMS denial, deploy failure):
finish the rest, then report exactly what failed, what state it is in, and
the next lever (e.g. roomres@haas.berkeley.edu for rooms, the organizer
pushing the deploy themselves). Never silently skip; never retry-loop a
failing login.
